# Приёмка и доставка

## Проверка истории

Если пользователь не запросил другой формат, проверь презентацию по [эталону стойки](server-rack-standard.md): тёмно-зелёная обложка с ответом, светлые содержательные главы, обычная вертикальная прокрутка, визуалы по теме и доступное досье. Прежний образец K2 не является текущим стандартом.

Проверь открытие отдельно от остального документа: тема названа, предыстория понятна, причина продолжить конкретна. При возможности дай его независимому читателю на 10–15 секунд и попроси пересказать тему и интерес. Если тест выполнен только агентом, обозначь это как редакционную проверку.

Затем прочитай основную линию без раскрытия справочных блоков. Она должна связывать главы и отвечать на обещание открытия. Сверь числа, даты, имена, единицы и подписи с реестром; проверь, что сокращение не изменило смысл и не убрало важное ограничение.

## Визуальная проверка

1. Отрендери все разделы финального файла и просмотри каждый в читаемом размере.
2. Просмотри последовательность целиком: нет ли одинакового карточного ритма, случайных пустот, нескольких конкурирующих заголовков или плотности, которая мешает читать.
3. Проверь desktop 1280 px и телефон на 320, 375, 390 и 430 px, включая встроенный просмотр HTML на iPhone или в Telegram, если он доступен. На каждой ширине сравни `document.documentElement.scrollWidth` с `document.documentElement.clientWidth`, найди выходящие за окно элементы и устрани источник переполнения; таблицы перестраивай для узкого экрана, а широкие карты и навигацию прокручивай внутри собственного блока вместо маскировки ошибки через `overflow-x: hidden`. Для сложной композиции добавь 1024 px или 1440 px.
4. Исправь обрезку, наложения, неожиданные переносы, горизонтальный выход страницы, пропавшие изображения и нечитаемые подписи. Проверь текст при увеличении до 200%.
5. После последней правки пересмотри финальную версию; при локальном исправлении дополнительно проверь связанные размеры и соседние блоки.

Для PPTX используй renderer и overflow test своего presentation workflow. Для HTML сначала запусти:

```bash
node scripts/verify.mjs /absolute/path/presentation.html
```

Затем запусти `node scripts/verify-mobile-width.cjs /absolute/path/presentation.html /absolute/path/mobile-qa.json` и тот же тест с `BROWSER=webkit` на iPhone-подобном движке; оба отчёта должны иметь `passed: true` при включённом и отключённом JavaScript. Эмуляция не заменяет проверку реального iPhone или Telegram-просмотрщика, когда они доступны.

Должно быть `FAIL 0`. Предупреждение об inline JavaScript требует проверки базовой версии, а не автоматического удаления анимации. Статический проверяющий скрипт не подтверждает автономность динамически загружаемых данных, качество текста, контраст или успешную доставку. Если визуальная проверка недоступна, не объявляй файл готовым для телефона или Telegram по статическому PASS либо рендеру другого формата.

Проверка блокирует выпуск без видимой шапки происхождения MarkInfo. Сверь источник, точное название задачи, безопасный код сессии и полный набор хэштегов с [контрактом шапки](markinfo-provenance.md). Для файлов, собранных модулем `bot.html_provenance` подключённого проекта Technopack, дополнительно выполни:

```bash
python3 -m bot.html_provenance check /absolute/path/presentation.html
```

При поиске текстовых заглушек проверяй читаемое содержимое, исключая код JavaScript и CSS, чтобы ключевые слова языка не становились ложными ошибками документа.

При подозрении на сбой эмуляции жеста воспроизводи его на минимальной странице без кода просмотрщика и фиксируй реальные события и их время, прежде чем менять рабочий интерфейс ради теста.

## HTML и взаимодействие

- Отключи JavaScript: весь материал, изображения, якоря, раскрытия, ссылки и текст для копирования должны быть доступны.
- Проверь reduced motion: нет пространственного движения и принудительной плавной прокрутки; смысл и доступ к функциям сохранены.
- Проверь нативные ссылки, `details`, клавиатурный Tab, видимый фокус и реакцию на нажатие. Навигация не перекрывает целевой заголовок.
- Проверь, что каждая ссылка на внешний ресурс открывает новую вкладку и содержит `rel="noopener noreferrer"`, а якоря оглавления прокручивают текущий документ.
- Проверь контраст обычного текста не ниже 4.5:1, крупного — 3:1; не полагайся на цвет для различения статусов.
- Проверь отсутствие обязательных внешних запросов. Открой копию standalone-файла из другой папки; при отключённой сети всё содержимое должно сохраниться.
- Проверь print-стили и печать справочных блоков; если PDF входит в результат, просмотри сам PDF.
- Для анимаций проверь быстрое повторное действие и изменение reduced motion во время просмотра. Ввод не блокируется, отменённое движение не оставляет скрытый контент.

Если изображения открываются крупно, выполни [матрицу проверки просмотра фото](photo-viewer.md): на телефоне проверь двойной тап прямо из карточки и внутри открытого фото, закрытие полного кадра вертикальным свайпом и возврат после короткого движения; на компьютере — щелчок. Перемещение увеличенного кадра не должно вызывать закрытие или ложный click после drag. В итоговой записи отделяй статические проверки, тесты обработчиков событий, наблюдаемое поведение в браузере и проверку на реальном устройстве. Отсутствие ошибок в консоли или наличие кнопки в DOM не подтверждает доступность закрытия, изменение масштаба и правильную точку возврата.

При печати выбранные варианты и ограничения должны читаться на бумаге независимо от экранной темы; справочные блоки раскрываются, а диалоги и их затемнение не перекрывают документ. Проверь фактический печатный вид, а не только наличие `@media print`.

## Доставка владельцу

Автономный HTML остаётся основным файлом. PPTX создавай по прямому запросу, PDF — как согласованный дополнительный формат. Не отправляй scratch-файлы и исходный код без запроса.

По постоянному маршруту владельца используй только OpenClaw MarkInfo dispatcher. Перед запуском проверь актуальную среду и разрешённый путь dispatcher; не переключай хост или получателя по предположению.

Сопроводительная аннотация короткая: тематический значок, жирный заголовок, главный вывод, заметные ключевые цифры, существенное ограничение и одно действие. Сохраняй Telegram HTML-форматирование.

Считай новую или обновлённую презентацию доставленной после проверки квитанции с `@markiinfo_bot`, типом чата `private` и `message_id`. Сохраняй связь квитанции с фактическим файлом и его SHA-256. Если отправка не удалась, сообщи точное состояние и не заявляй доставку. Для дополнительных адресатов нужно отдельное явное разрешение.

После подтверждённой доставки не перезаписывай выданную версию: исправление получает новый файл, SHA-256 и квитанцию. При изменении только интерфейса сохрани принятые тексты, изображения, выбранные варианты и их происхождение; не запускай повторную генерацию визуализаций без задачи на их изменение.

Подтверждённо готовый файл выдавай без задержки из-за общих длительных проверок; незавершённую обязательную регрессию обозначай отдельным статусом. Локальная ссылка не заменяет установленную доставку.
